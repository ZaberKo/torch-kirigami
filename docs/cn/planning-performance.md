# 剪枝规划性能优化

本文说明依赖分析与 `Pruner.plan()` 的性能改造。历史性能优化不改变剪枝执行契约；当前预算已统一为剪枝后剩余量上限，评分接口为 `Metric.score(context, candidates, accepted_impact=...)`，其中 `accepted_impact` 表示已经接受的删除请求及其完整依赖影响，模型尚未执行物理剪枝。选择接口为 `Strategy.select(context)`。下文历史基准使用当时的静态评分，不能直接用于比较新评分或动态策略的耗时。

## 1. 问题与处理原则

规划主要处理 Python 对象、符号索引、约束和修改配方。模型参数位于 CUDA 并不意味着这些计算也在 GPU 上执行。主要重复工作包括：逐个合并大量通道请求、为无关轴保存空结果、遍历不相关候选和算子、重复读取模型属性，以及反复构造相同的尺寸信息。

改造采用三条原则：

1. 对确定不变的图结构建立索引，减少全表扫描。
2. 对同一次分析中的相同输入复用读取与计算结果。
3. 候选组合仍进行联合传播、完整约束检查和执行验证；局部摘要不能代替这些检查。

## 2. 依赖分析

实现位置：[graph.py](../../torch_kirigami/graph.py)、[selection.py](../../torch_kirigami/selection.py)。

| 改造 | 原有开销 | 当前处理与边界 |
| --- | --- | --- |
| 合并简单初始请求 | 每添加一个通道，都对不断增长的区域集合做差集和并集 | 同一张量、同一变化轴且通过复杂度检查的请求先合并索引，再进入原工作队列；复杂区域及扩展类型使用通用路径 |
| 约束索引 | 每次查询重新检查所有图内约束 | 精确内置类型按引用张量索引；未触及部分保留空请求的检查结果；自定义约束、子类及调用方附加约束仍逐次检查 |
| 受影响调用索引 | 每次查询扫描所有调用和输入表达式 | 建图时记录张量到直接调用、调用到后继调用的邻接关系；查询只遍历可达调用 |
| 规范化索引的直接判断 | 边界和简单形状判断也执行区域差集 | 利用有序、互不重叠区间及单个笛卡尔积区域的性质；一般多区域情况继续使用原有集合算法 |

初始请求的合并只改变进入工作队列前的集合计算。`Impact.requested` 保留原始请求，索引仍使用原坐标，传播结果和原因记录不变；不把多个独立 `Impact` 的并集当作联合分析。复杂度限制及非法输入检查仍然有效。

受影响范围不以输出尺寸是否变化为界。归约、切片或布局变化之后，即使某个输出 shape 不变，其下游调用也继续接受执行检查。邻接表仅存储直接边，不预先保存所有节点之间的传递闭包。含扩展子类的尺寸表达式保留逐次求取引用的路径，避免把扩展声明中的动态行为固化。

## 3. Greedy 搜索

实现位置：[strategies.py](../../torch_kirigami/pruning/strategies.py)、[planner.py](../../torch_kirigami/pruning/planner.py)。

- **稀疏候选摘要**：只记录候选实际影响的轴及索引集合，省去候选与所有轴的空组合。摘要用于提出满足结构约束的组合，不用于直接生成剪枝配方。原先按删除量上限排除请求的路径已删除。
- **按轴索引候选**：为每个轴保存按原评分顺序排列的贡献候选。补全约束时先访问相关候选；随后仍保留完整的全局排序回退，覆盖单独没有效果、组合后才产生影响的候选。
- **按需遍历**：找到可用补选项后不继续构造全部剩余候选列表；有帮助的候选及回退候选的相对次序保持不变。
- **统一预算目标**：预算模块统一比较“剩余量 ≤ 目标”；参数量按实际张量配方计算，通道宽度按联合影响去重计算。参数预算不构建无用途的通道摘要。局部超额完成不能抵消另一轴的欠达；每次接受追加后检查目标，达标立即停止，不额外进行动态评分。

`Balanced`、`Divisible` 的计数预估仍只用于经过审查的精确内置类型。实际提交前重新传播全部请求并检查约束、预算和执行支持。预估失败或首次组合失败，不意味着该轴永久固定；原有联合补全和合法替代候选搜索仍然保留。

`max_trials` 仍统计联合尝试，缓存命中也计入。不会通过提高默认限额、改变候选包装或预先固定相邻通道块来掩盖重复计算。

### 评分与动态选择

- `Greedy` 只在开始时评分；`DynamicGreedy` 每接受一组完整合法的删除后重新评分、排序。两者共用约束补全、预算核算和执行检查。
- 所有 metric 均使用有界批次，单个候选的分数不能依赖同批次有哪些候选。多个请求的联合评分需显式构造一个 `Candidate`，不默认把分数相加。
- 条件评分先联合传播“已选请求 + 新候选”，再排除已选参数区域；不能只从候选的独立影响中做差，否则会漏掉组合后才触发的依赖。
- `GroupMagnitude` 以候选逻辑轴的全部剩余单位置能量均值归一化，分母不随 batch、候选子集或块包装变化。缓存限于同一规划上下文、最多 32 项轴记录，只保留归一化常量和每个位置的标量分数；参数版本变化时重算。单通道候选复用已经算出的精确分数，多通道组合仍做联合评分，不假定可加。
- 动态策略会增加依赖查询和评分次数。`max_trials` 限制联合搜索尝试，不限制评分耗时；动态评分也不重新运行模型或更新梯度。

原 workflow 的单层输出权重评分已删除，普通 magnitude 工作流统一使用库内 `GroupMagnitude`。以下历史基准保留用于说明原数据结构优化效果，不代表新评分得出相同计划或具有相同耗时。完整接口见[规划设计](../pruning-design.md#scoring-and-strategy-contracts)。

### 独立轴上的精确评分复用

`Greedy` 和 `DynamicGreedy` 现在会先判断整个候选空间是否满足以下条件：候选只选择一个轴位置；依赖关系是可证明的一一对应；不同轴域不共享张量。该判断使用现有关系声明，不按模型名称或模块路径匹配。

满足条件时：

1. 沿对应轴批量计算所有相关权重的 L1/L2 统计，包括下游输入权重及受支持的归一化权重，并按参数实体去重。张量运算在参数所在设备上执行，复用与通用路径相同的数值归约公式。
2. 动态策略接受删除后，保留位置的原始权重统计不变；重新计算剩余位置的归一化分母，再对候选排序。因此仍是条件评分，不退回静态排序。
3. 根据已证明的对应关系生成稀疏轴摘要，省去逐候选重复传播。每次拟接受的组合仍进行完整联合传播、约束检查、预算计算和配方编译。
4. 每个逻辑轴用有界的临时集合查询已删位置，避免排序时反复枚举索引区间。存储量与逻辑通道数有关，不为激活元素建立标签。

实现集中于 [ranking.py](../../torch_kirigami/pruning/ranking.py)。仅精确内置 `GroupMagnitude` 且没有参数过滤器时启用；自定义 metric、关系或约束、分区映射、共享权重行列交叠、无法证明的 reshape、inference tensor，以及将删除最后一个位置的评分使用原通用路径。广播只在目标轴位置保持一一对应时参与证明；同 shape 的 reshape 也必须已有明确的行主序关系声明，不能据 shape 猜测算子语义。

统计仅在一次选择调用内保留。每轮仍检查模型有效性及参数/buffer 版本；值发生已检测的更新时退出复用。普通权重训练不属于同一次规划过程。该优化不修改依赖核心、公开接口、评分定义或执行支持边界；批量浮点归约可能存在通常的舍入差异。

基础剪枝和迭代剪枝默认覆盖每个 block 的内部宽度：ResNet-18/34 的 `conv1`、ResNet-50 的 `conv1` 和 `conv2`、ViT 的 FFN 中间维度；保留 block 外部接口。Isomorphic 保留较广的候选发现，使用各结构类别独立配额及外层比例搜索；OSSCAR 使用重建求解器后提交精确请求，均不调用 `Greedy`。比较性能时必须同时注明候选范围、算法和校准配置，不能把它们的查询次数与 Greedy 的尝试次数直接等同。库的通用候选发现能力不受基础示例默认范围限制。

## 4. 状态检查与配方编译

实现位置：[capture.py](../../torch_kirigami/capture.py)、[configuration.py](../../torch_kirigami/configuration.py)、[bindings.py](../../torch_kirigami/bindings.py)、[rewrite.py](../../torch_kirigami/pruning/rewrite.py)、[validation.py](../../torch_kirigami/pruning/validation.py)。

| 改造 | 复用范围 | 仍执行的检查 |
| --- | --- | --- |
| 模块属性及 slot 信息共用 | 单次 fingerprint 内 | 模式、配置、注册绑定、普通属性引用、别名和 hook 状态 |
| 默认声明式 lowering 减少重复 fingerprint | 一次配方编译内部 | 入口、出口和自定义 lowering 返回或抛错后的状态验证 |
| 执行要求索引 | 单次配方编译内 | 原声明顺序、重复调用、根模块及不透明模块的后代属性归属；未处理要求仍报错 |
| 紧凑尺寸记忆 | 单次 forward 验证内 | 分组配方决定的实际形状、原坐标对应、stride、别名和原始调用参数 |

属性读取结果不跨 fingerprint 保存。不同候选即使产生相同 shape，也不能据此复用整份执行证明：删除不同原坐标可能改变静态切片含义、分组布局或共享参数要求。

现有查询与配方缓存继续有界。模型更新使相应缓存失效；最终计划仍独立验证，`apply()` 仍重新检查执行前提。本次改造不扩大原有状态检测能力，也不承诺识别所有任意 Python 副作用或权重写入方式。

## 5. 后续方向与未采用方案

### 可继续评估、尚未实施

| 方向 | 预期作用 | 实施前提及优先级 |
| --- | --- | --- |
| 合并单次 fingerprint 内的注册表遍历 | 参数、buffer、模块和普通引用检查共用本次读取的注册信息 | 保留完整别名路径与唯一对象两种视图；状态检查仍是主要开销，优先评估 |
| 消除同一内部调用链中重复的状态检查 | 已验证状态且中间没有用户代码执行时，减少重复 fingerprint | 必须逐条证明回调边界；不能转为跨查询缓存或全局跳过检查，尚未实施 |
| 候选摘要的计算也按命中张量索引 | 当前存储已稀疏，但提取摘要时仍遍历待统计轴 | 先统一检查全部轴的归属，再只计算受影响轴；新采样中占比较小，优先级低 |

2026-09-23 的补充采样使用 768 候选 ViT 规划。主要累计开销集中于 fingerprint、属性修改后的重新捕获及紧凑元数据 forward 验证；候选轴摘要、受影响调用查找和执行要求索引已不是主要瓶颈。采样有额外开销，且嵌套函数累计时间重叠，不据此直接推算整体加速比。

### 当前不采用

| 方案 | 不采用的原因 |
| --- | --- |
| 跨试探请求复用可变传播状态 | 拒绝后回滚、跨边联合触发、原因记录和复杂度诊断容易产生新的状态错误 |
| 保存所有候选的完整 `Impact` | 候选数量大时占用大量内存；稀疏轴摘要已满足主要查找需求 |
| 仅按 shape 缓存执行证明 | 相同 shape 不能证明坐标、布局及原 forward 的语义相同 |
| 规划期间全局关闭有效性检查 | 自定义评分、关系和 lowering 可执行用户代码，不能假定模型始终不变 |
| 为静态评分引入堆或通用求解器 | 当前排序只做一次，主要瓶颈不在反复排序；额外框架增加复杂度 |

## 6. 验证方式

正确性回归同时检查集合代数、完整候选顺序、联合依赖和公开 build/plan/apply 流程。测试包含共享调用、分组及深度卷积、组合后才产生效果的候选、未触及约束的初始失败、自定义回调修改状态、stride 不能证明的拒绝，以及合法替代方案。

性能回归优先统计实际读取、遍历或计算次数，避免用受系统负载影响的秒数作为单元测试阈值。真实模型基准使用相同模型、输入、评分和预算，对比完整静态计划及应用后的张量；不能只凭运行加快或 forward 成功判断优化正确。

更多测试入口见[验证指南](../testing-coverage.md)。基准中的规划耗时不包含 ImageNet 评估、微调或 `torch.compile` 延迟测试。

本轮最终验证：当前环境执行 `pytest --require-cuda`，3,803 项通过，1 项跳过（跨设备测试的 CPU 参数分支）；Python 3.10 / PyTorch 2.6 CPU 相关套件 1,085 项通过，685 项 CUDA 参数用例跳过。Ruff、四个基础示例及打包检查通过。

## 7. 实测结果

2026-09-23，在 RTX 5070 Ti、Python 3.12、PyTorch 2.14.0+cu130 环境中，通过 `Granularity.by_path` 将 ViT-B/16 的 12 个 FFN 中间宽度对齐到 8，使用工作流的输出通道权重平方和评分（`--metric magnitude`）及全模型参数预算。基准进程的 PyTorch CPU 线程数固定为 2；库本身不修改线程设置。

| 对照 | 本轮改造前 | 本轮改造后 | 决策核对 |
| --- | ---: | ---: | --- |
| CPU，768 个候选，参数减少目标 0.5% | 9.50 s | 7.38 s | 均为 36 次联合尝试，选中 288 个候选 |
| CUDA，预训练模型，36,864 个候选，参数减少目标 5% | 356.83 s | 214.53 s | 均为 353 次联合尝试，选中 2,824 个候选 |

两组对照的完整可保存计划及应用后的 forward 输出均完全相同。完整 CUDA 基准的参数量均从 86,567,656 变为 82,227,168；152 个 `state_dict` 张量也逐个匹配原先保存的剪枝模型。

完整规划耗时进一步减少约 40%。这些是同一台共享主机上的单次记录，期间还执行了其他验证任务，并非隔离机器上的统计基准；不能把局部函数加速比相乘，也不能将该比例推广到所有网络。早先的 1,121.7 s 是工作流运行日志，未作为本轮改造前的计时基线。

## 9. 动态评分优化实测（2026-09-24）

对照旧源码快照 `f307533`。环境为 RTX 5070 Ti、Python 3.12、PyTorch 2.14.0+cu130，使用默认 20 个 PyTorch CPU 线程。均为 `DynamicGreedy(GroupMagnitude(p=2))`、5% 全模型参数减少目标、FFN 中间宽度对齐到 8；计时只覆盖 `Pruner.plan()`，不含加载权重、建图、apply、数据加载、训练或 compile。

| 模型与候选 | 优化前 | 优化后 | 依赖传播次数 | 验证 |
| --- | ---: | ---: | --- | --- |
| 两层小型 ViT，隐藏宽度 64、FFN 宽度 256，512 候选 | 14.10 s | 0.36 s | 5,616 → 8 | 6 次联合尝试、48 个选中候选；完整持久化计划和应用后参数逐字节一致 |
| 官方预训练 ViT-B/16，12 个 FFN，36,864 候选 | 600 s 超时，未完成 | 93.84 / 98.12 s | 旧版超时前 143,251 次；新版完整 355 次 | 353 次联合尝试，选中 2,824 个候选；apply 和 CUDA forward 成功 |

小型模型约加速 39 倍。按新版较慢的一次记录，完整模型只能确认至少约 6.1 倍，不能将超时阈值当作旧版完整耗时。完整模型参数从 86,567,656 减至 82,227,168，实际减少约 5.014%；略超过 5% 是通道对齐导致的离散步长。

完整模型第一版优化耗时 172.38 s；随后消除已删位置的重复枚举，降至 93.84 s，最终代码复测 98.12 s。这三次优化后的完整计划、全部状态张量哈希和 forward 输出一致。旧版完整动态计划没有跑完，因此不声称已与它进行完整结果比较。正确性另由小型模型与通用逐候选联合评分的公开 plan/保存恢复/apply 对照覆盖。

两次小型重复测量分别为旧版 14.30/14.10 s、新版 0.33/0.36 s。记录来自共享主机，期间有其他验证进程，不是隔离环境的统计基准；不能将这些加速比推广到复杂共享结构、自定义评分或 head+FFN 的混合候选空间。历史静态评分的耗时不作为本次动态优化的基线。

验证：规划、集成、架构与持久化套件以 `--require-cuda` 执行，2,761 项通过，1 项跳过（跨设备测试的 CPU 参数分支）。最终评分与优化专项 138 项通过；新增独立轴测试共 59 项，包含通用路径对照、独立数值参考及公开计划恢复与执行。Python 3.10 / PyTorch 2.6 CPU 最终专项 106 项通过，53 项 CUDA 参数用例按环境跳过。Ruff 和格式检查通过；CPU 兼容结果不作为 GPU 验收依据。

### 同版本静态与动态对照

随后使用上述优化后的同一份代码，按静态、动态、静态、动态的顺序串行复测，每次使用独立进程。配置对应 `prune_finetune.py --model vit_b_16 --device cuda --pruning_ratio 0.05 --granularity 8 --metric magnitude`：官方预训练权重、seed=7、12 个 FFN、36,864 个候选，建图样例为全零 `[1, 3, 224, 224]` CUDA 张量。仅计时规划，不运行 ImageNet 评估、微调或延迟编译。

| 策略 | 第一次 | 第二次 | 两次均值 |
| --- | ---: | ---: | ---: |
| `Greedy`（`--selection static`，CLI 默认） | 63.40 s | 70.62 s | 67.01 s |
| `DynamicGreedy`（`--selection dynamic`） | 105.52 s | 109.75 s | 107.63 s |

同版本动态规划约为静态的 1.61 倍耗时。此前旧版静态的 200 多秒与新版动态的 100 秒左右是跨实现比较，不能据此判断动态比静态快。独立轴统计复用同时加速两种策略；动态仍有每轮条件评分更新和重新排序的额外工作。`--compile_latency` 只影响延迟测量，不将规划编译为 GPU 程序。

四次均完成 353 次联合尝试、355 次依赖传播，删除 2,824 个候选，最终参数量 82,227,168。同策略两次的完整保存计划、状态张量哈希和输出完全一致。静态与动态共有 2,072 个选中候选，各有 752 个独有选择，不能视为相同计划。此次没有比较 ImageNet 精度；两次计时也不构成隔离环境中的统计性能保证。

## 10. 约束补选与元数据计算复用（2026-10-01）

本轮依据当前代码和实测瓶颈选择优化，不以论文中的交替优化或归一化公式代替依赖求解正确性证明。[TriSP](https://arxiv.org/html/2607.22587) 使用 z-score 标准化，第 5 节是结论；[SparseLLM](https://arxiv.org/html/2402.17946) 交替优化权重、mask 和辅助变量，未证明本库的增量依赖传播。

### 实现

1. **补选提前排除已用候选。** `_completion_order()` 在构造索引差集前跳过当前请求中已有的候选；其余候选的评分顺序、分区偏好和完整回退顺序不变。单独没有贡献但组合后有效的候选仍进入回退查询。
2. **按调用复用纯元数据输出。** 内置规则声明 `cache_meta_output`，仅对保证产生新输出、且不修改输入的元数据计算启用。缓存键包含实际参数容器和标量、输入及模块绑定的 shape/stride/dtype/offset/flags，以及相关属性修改。每个 FX 调用最多保留一份输出事实，命中时创建独立 meta 张量，不保留真实权重或激活。Tensor 子类、未知参数或额外输出元数据使用原执行路径。
3. **复用不变轴映射。** 依赖图对深度不可变的精确内置 `AxisRelation`，按关系端点保留最后一次输入区域及对应输出选择。缓存不含完整 Impact，也不合并独立闭包。每次查询仍从原始请求运行完整工作队列，合并选择、生成来源、检查全部相关约束与修改要求；累计输入变化后重新计算完整映射。扩展及失败映射不缓存。

元数据缓存只复用原生计算结果：slice/split 索引对应、view 布局证明、原地消费者安全、输出形状及布局未知状态仍逐次检查。相同 shape 不构成执行证明。参数/buffer 版本变化会清空规划上下文中的元数据和编译缓存，最终独立上下文重新验证计划。属性修改后的 FX 重捕获继续执行，避免漏掉原 Python forward 中变化的分支、循环、常量或索引用途。

### 对照测量

以改前源码快照 `fcac8b2` 对照本轮实现，按“改前静态、改后静态、改前动态、改后动态”串行运行独立进程。RTX 5070 Ti、Python 3.12、PyTorch 2.14.0+cu130；官方预训练 ViT-B/16、seed=7、全零 CUDA 样例 `[1, 3, 224, 224]`、12 个 FFN、36,864 候选、参数减少目标 5%、granularity=8、`GroupMagnitude(p=2)`。计时仅覆盖规划，采用函数边界计时，不启用逐函数事件 profiler。

| 策略 | 改前 | 改后 | 耗时减少 |
| --- | ---: | ---: | ---: |
| `Greedy` | 92.25 s | 50.17 s | 45.6% |
| `DynamicGreedy` | 137.47 s | 117.30 s | 14.7% |

静态补选耗时从 24.22 s 减至 1.56 s，元数据 forward 检查从 24.03 s 减至 6.01 s。动态策略每轮更新排名，因此原本补选时就不会扫描大量已接受候选；其收益主要来自元数据复用，元数据检查从 23.54 s 减至 5.72 s。动态评分及排序仍耗时约 59 s，没有退回静态评分。上述子阶段部分嵌套，不能直接相加为总耗时。

四次均完成 353 次联合尝试、355 次传播调用，选择 2,824 个候选。每个策略改前、改后的完整持久化计划、应用后的全部模型状态哈希及 CUDA forward 输出一致；不声称静态与动态计划相同。这是共享主机上的单次对照，不保证其他模型或每次运行获得相同比例的收益。

### 验证与暂未采用的方向

全量 CPU/CUDA 回归使用 `--require-cuda`：4,305 项通过，1 项为跨设备用例的 CPU 参数分支跳过。最终新增边界、补选与架构专项复测 60 项通过；最低 Python 3.10 / PyTorch 2.6 CPU 相关套件 116 项通过、54 项 CUDA 用例跳过。Ruff 和格式检查通过；CPU 环境的 CUDA 跳过不作为 GPU 验收。

本轮没有扩展其他 metric 的独立统计快路径、规范化完整 Impact 缓存键、扩大缓存容量或引入多进程。默认 workflow 已使用批量统计的 `GroupMagnitude`；权重统计不足 0.5 s，扩大缓存对不断增长的新请求帮助有限。完整 Impact 还包含原始请求、来源和限额诊断，不能仅按选择并集共享结果。本轮也未引入跨查询暖启动闭包及失败尝试回滚状态；纯关系映射复用保留完整查询流程，改动和证明范围更小。

## 预算职责与搜索边界

[`pruning/budget.py`](../../torch_kirigami/pruning/budget.py) 集中处理目标解析、计量、比较和报告。它不查询依赖图、不编译配方、不参与评分或模型修改。`PlanningContext` 提供已经验证的联合影响和配方；Greedy/DynamicGreedy 不再判断具体预算类型，也不再调用预算专用 `admissible()`。

所有自动预算都必须达标；必要的整组联动允许多删，欠达则报错且不修改模型。多轮通道预算始终使用最初宽度换算剩余量上限，避免对已超额完成的轴再次要求删除。这里改变了旧通道预算允许欠达的语义，历史耗时不能视为新语义下的基准。
